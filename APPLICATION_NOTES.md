# Project Aphelion - application notes

Submission for the Razorpay AI Buildathon, AI Revenue Recovery track.

## What it is, in one paragraph

Project Aphelion is a closed-loop revenue-recovery system for failed payments. A failure arrives over a Razorpay webhook; the system diagnoses it, scores the probability of recovery with a calibrated model, computes a bounded set of allowed actions, lets an LLM choose one and explain it, re-checks that choice through a deterministic policy gate, creates a Razorpay Payment Link where warranted, and attributes recovered rupees only when a real payment confirms. Every step is auditable, and the AI has no authority over money.

## Why it fits the track

Revenue recovery is a targeting and safety problem, not a chatbot problem. Contacting every failed payment wastes money and goodwill; contacting none leaves revenue on the table; contacting the wrong ones annoys good customers and risks acting on fraud. Project Aphelion treats it as what it is: a bounded, measurable, auditable decision problem where AI helps with judgment but never holds the pen on money.

## The core thesis

> AI decides within boundaries. Deterministic code enforces the boundaries.

The control path is always `deterministic facts -> risk and policy -> bounded AI reasoning -> deterministic gate -> action -> verification`, and never `LLM -> arbitrary API -> money`. The LLM only ever selects from an action set fixed before it runs, and returns a strict JSON object with no amounts or probabilities it could fabricate. Money math, payment state, idempotency, signature checks, policy limits, and recovered-amount attribution are all deterministic.

## What is real, and what is simulated (stated plainly)

- Razorpay integration is real code: HMAC-SHA256 webhook verification over the raw body, and Payment Links via `POST /v1/payment_links/`. It runs in `razorpay_test` (Razorpay Test Mode, no live money) or a deterministic `mock` mode that needs no credentials.
- Live Test Mode end-to-end validation is pending merchant test credentials. The integration path and the signature and payload contracts are implemented and unit tested; a full run against live test payments has not been performed here because no credentials are configured. This is stated rather than fabricated.
- The evaluation is a Synthetic evaluation, labelled as such throughout. Relative comparisons (policy versus policy, component versus component) are meaningful; the absolute rates are not market numbers.

## Engineering highlights

- Deterministic policy gate independent of the AI, re-checked on every action (opt-out, fraud, already-paid, attempts, cooldown, daily budget, value bounds).
- From-scratch calibrated logistic regression in TypeScript, so training and evaluation run in one reproducible toolchain (no Python dependency). Training is deterministic: identical weights and metrics every run.
- Held-out, leak-free evaluation with a customer-group split, baselines (no-action, contact-all, rules, ML-only), a budgeted targeting curve, an ablation, and an agent-safety section. Regenerated by `npm run eval`; the dashboard and README read the same numbers.
- Reliability: idempotent webhooks (atomic event-id claim), an explicit payment and case state machine, per-payment serialization in the worker so concurrent deliveries cannot interleave, and safe failure modes throughout.
- Prompt-injection defense by construction: the allowed action set is fixed before the model runs, untrusted text is delimited data, and output is schema-validated with a deterministic fallback.
- Ports-and-adapters persistence (Postgres and in-memory), validated against a real Postgres. HTTP hardening: raw-body signature parsing, body limit, request timeout, security headers, per-IP rate limiting.
- Operations dashboard (overview, recovery queue, case detail with decision factors and audit timeline, evaluation, editable policy) with loading, empty, and error states and a responsive layout.
- 56 tests (unit, integration, security, HTTP end to end), plus lint, typecheck, build, and a CI workflow. Docker Compose brings up Postgres and the API.

## Metrics snapshot (Synthetic evaluation, held-out, seed 42)

- Recovery model: ROC-AUC about 0.70, PR-AUC about 0.62, ECE about 0.05, base rate about 0.38.
- Targeting: the top 10 percent by score convert at about 76 percent, roughly twice the base rate.
- Value: recovers about 99 percent of the revenue that contacting everyone would, with about a quarter fewer and safer contacts.
- Agent safety: 100 percent valid decisions, 0 policy violations, unsafe actions rejected, injection ignored, deterministic fallback on a broken model.

Honest ablation: the calibrated model drives targeting quality. The bounded LLM does not change the business numbers; its value is validity, safety, and explanation. This is reported rather than hidden.

## A real failure found during development

An out-of-order integration test caught a bug where a `payment.captured` arriving before a `payment.failed` for the same id was dropped, so a later stale failure created the payment as failed. Fixed by making capture upsert-create as captured; the state machine then rejects the stale downgrade. A regression test guards it. Full write-up in [ARCHITECTURE.md](ARCHITECTURE.md#a-real-failure-and-the-fix).

## Honest limitations

- The evaluation is synthetic; absolute rates are not market numbers.
- Live Razorpay Test Mode end-to-end has not been measured (needs test credentials).
- The worker is in-process; horizontal scale needs a durable queue (the seam is isolated).
- Single-merchant tenancy in the demo, though the data model supports multiple merchants.
