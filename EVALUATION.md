# RecoverAI Evaluation

This report is generated by `npm run eval`. All numbers below come from a held-out
test split of a reproducible synthetic dataset. This is a Synthetic evaluation: it
measures targeting and decision quality in a controlled environment, not live money.

## Dataset

- Seed: 42 (fully reproducible via `npm run gen:dataset`)
- Total cases: 2000
- Split: group split by customer (70/15/15)
- Train / Val / Test: 1401 / 259 / 340

The label is "would this customer pay if sent a recovery link", an exact function of
the generator. Features are decision-time observables only (amount, method, failure
type, prior payment history, timing). A latent per-customer reliability drives the
outcome but is never shown to the model, so the model must learn a real signal.

calibrated on the validation split; the test split below never influenced either.

## Budgeted targeting (the core money story)

Recovery teams cannot contact every failed payment (contact fatigue, opt-out risk,
operational limits). Under a fixed contact budget, the question is which cases to
contact. Each strategy ranks cases by its own priority and we contact the top ones:

- random: arbitrary order (floor)
- by_amount: contact the largest failed payments first (a common human heuristic)
- recoverai: rank by calibrated expected recovery (probability times amount)

The calibrated ML model is what drives targeting quality (recovered per link) over the
rules baseline. The bounded LLM layer does not change these business numbers: it selects
among the deterministically allowed actions and writes the explanation. Its value is
measured separately below (validity, safety, injection resistance), which is the honest
finding: AI reasoning improves explainability and handles bounded ambiguity, while the
deterministic engine owns the money outcomes.

## Limitations

- Synthetic evaluation. Real recovery rates depend on customer base, offer, and channel.
  The generator encodes plausible but invented relationships; do not read these as market rates.
- The outcome oracle is a modelled probability, not observed behaviour. The value of the
  numbers is relative (policy vs policy, component vs component), not absolute.
- The bounded LLM layer is evaluated with a deterministic mock provider in the batch, so
  business metrics are reproducible. Live-model behaviour is exercised separately by tests.
- Not yet measured: recovery against real Razorpay Test Mode payments end to end.
